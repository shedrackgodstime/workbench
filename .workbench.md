# Workbench Identity

`workbench` is the source repository for Shedrack Godstime's technical record.

It is designed to organize the material behind a long-term professional identity: project records, investigations, experiments, research notes, technical drafts, and learning records. Its purpose is to preserve the development of ideas from early curiosity through structured understanding, practical implementation, and eventual public presentation.

The repository is intentionally broader than a research archive, a blog source, or a project index. It reflects a technical practice centered on cybersecurity and extended through systems programming, networking, Linux, protocols, infrastructure, open source software, and emerging hardware-adjacent domains.

## Purpose

The purpose of `workbench` is to create a disciplined home for technical range.

Shedrack's work does not fit cleanly into one narrow category. Cybersecurity remains the central professional direction, but meaningful security work depends on understanding the systems around it: operating systems, networks, protocols, software architecture, infrastructure, hardware interfaces, and the constraints under which real systems fail.

`workbench` exists to make that range coherent. It provides a place to capture both the context around finished artifacts and the investigations that lead to them.

It also corrects a problem in the old portfolio model. Previously, public project content lived as `portfolio.md` files inside individual GitHub repositories, while research-style material lived in a separate repository. That made the portfolio depend on scattered presentation files across unrelated codebases. `workbench` centralizes the technical record without taking ownership away from the actual project repositories.

## Scope

This repository may contain:

- project records for software projects and prototypes
- open source work
- Rust crates and systems tools
- security research and investigations
- networking and protocol studies
- Linux and infrastructure notes
- technical experiments
- hardware-adjacent research, including satellites, LoRa, ESP32, drones, radio, and embedded systems
- drafts that may later become public portfolio material

Completeness is not required for inclusion. A subject can begin as reading notes, develop into an investigation, produce experiments, and later become a project, case study, or public article.

The repository values continuity of thought as much as finished output.

## Repository Model

The preferred structure is intentionally simple:

```txt
workbench/
  projects/
  explorations/
```

This model separates records of built artifacts from investigative work without fragmenting the repository into too many presentation-driven categories.

The model does not mean every project source tree belongs inside `workbench`. Each substantial project can keep its own repository. `workbench` holds the explanation, context, decisions, public-facing summary, research trail, and portfolio-ready material around that project.

The internal shape of each entry can evolve naturally. Some entries may need only one file. Others may later grow supporting notes, diagrams, logs, references, or decision records. The structure should allow that growth without requiring it upfront.

### `projects/`

`projects/` contains records of work centered on artifacts.

This includes software, tools, libraries, applications, infrastructure, prototypes, and open source projects. The defining characteristic is that the work produces something usable, demonstrable, published, or technically concrete.

The actual code for a project may live in its own repository. The `projects/` entry exists to explain the project: what it is, why it exists, how it works, what decisions shaped it, what was learned, and how it should be presented publicly.

Examples include:

- Rust crates
- command-line tools
- security utilities
- networking tools
- Linux utilities
- web applications
- infrastructure prototypes
- open source projects such as `irosh`

The guiding distinction:

> If the primary outcome is something built, its technical record belongs in `projects/`.

### `explorations/`

`explorations/` contains work centered on inquiry.

This includes research, technical notes, learning trails, experiments, protocol analysis, threat models, systems study, and hardware-adjacent topics that may not yet have practical implementation behind them.

Examples include:

- TCP/IP internals
- NAT traversal
- Linux networking
- operating system concepts
- satellite communication
- LoRa
- ESP32
- drones
- radio systems
- embedded security
- cybersecurity investigations
- CTF-style study

The guiding distinction:

> If the primary outcome is understanding, it belongs in `explorations/`.

An exploration may be theoretical, incomplete, resource-limited, or paused. Its value is in the structured pursuit of understanding, not only in immediate practical output.

## Writing And Presentation

Writing is treated as a format, not as a top-level source category.

A polished explanation of LoRa belongs with the LoRa exploration. A technical case study for `irosh` belongs with the `irosh` project. This keeps context close to the work that produced it.

The public portfolio may later choose to present selected material as essays, case studies, project pages, or research notes. Those labels belong to the presentation layer, not to the source organization.

## Initial Publishing Model

For the first version of portfolio integration, each public entry exposes one primary Markdown file: `README.md`.

That file is the version the site reads and displays. It should carry the complete public narrative for the project or exploration: the summary, context, technical details, important links, status, lessons, and anything needed for the entry to stand on its own in the portfolio.

This keeps the publishing model simple:

```txt
projects/<name>/README.md
explorations/<topic>/README.md
```

Using `README.md` keeps each folder understandable when viewed directly in the repository and gives the portfolio one predictable entry point to read.

`README.md` does not need to be the only file in an entry. Other files may exist beside it for deeper, rougher, or more specialized material:

```txt
projects/irosh/
  README.md
  architecture.md
  decisions.md
  notes.md
  references.md

explorations/lora/
  README.md
  notes.md
  questions.md
  references.md
```

Those supporting files can hold working notes, detailed research, design decisions, references, diagrams, logs, or unfinished thinking. The portfolio does not need to read them by default. They support the workbench; `README.md` represents the entry publicly.

This avoids returning to the old model where portfolio content was scattered as `portfolio.md` files across many separate project repositories. The public narrative lives in `workbench`; the project code can remain in its own repository.

## Relationship To The Portfolio

`workbench` is the source of truth for technical material. Individual project repositories remain the source of truth for their code. The portfolio is the public presentation layer.

The intended flow is:

```txt
workbench -> selected public material -> portfolio
```

The portfolio can highlight featured projects, active explorations, recent updates, selected notes, case studies, and current focus areas. Its job is to communicate clearly to visitors. The job of `workbench` is to preserve and organize the technical record behind that presentation.

This distinction keeps the portfolio clean, keeps project repositories focused on their actual code, and allows the underlying technical record to remain rich, honest, and evolving.

## Maturity

Entries in `workbench` may exist at different stages of maturity.

Useful maturity labels include:

- `seed`: an early idea, question, or reading trail
- `active`: currently being built or investigated
- `paused`: valid work that is not currently active
- `built`: a working artifact exists
- `published`: selected for public presentation or external release
- `archived`: retained for reference but no longer active

These labels are descriptive. They exist to clarify the state of work, not to create administrative overhead.

## Guiding Principle

`workbench` should organize breadth without diluting focus.

It should make visible the connection between cybersecurity, systems programming, networking, Linux, infrastructure, open source software, and emerging technical interests. The structure should support long-term focus while leaving enough room for curiosity to become serious work.

The core model remains:

> `projects/` records the context around what is built. `explorations/` records what is investigated.

That distinction gives the repository its shape.
